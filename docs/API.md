# Контракт серверного API
## Система цифрового контроля залоговых активов «Микрокредитбанк»

Версия 0.2 · Редакция от 24.08.2026 · Основание: ТЗ v2.0, раздел 8

---

## 1. Назначение документа

Раздел 8 ТЗ фиксирует серверную часть как содержание следующего этапа, но не
описывает её. Настоящий документ закрывает этот пробел: он задаёт контракт,
против которого клиент прототипа заменяет `malumot.js` на реальные вызовы,
не меняя ни одного экрана.

Документ описывает **интерфейс**, а не реализацию. Выбор языка, фреймворка,
СУБД и схемы развёртывания остаётся за исполнителем этапа и здесь намеренно
не предрешается.

### 1.1 Что уже готово на стороне клиента

Прототип приведён к состоянию, в котором подключение сервера — механическая
операция:

- все сущности собраны в одном модуле `malumot.js` и публикуются через
  `window.MKB_DATA`; страницы не содержат собственных массивов данных;
- объекты залога адресуются идентификатором, а не текстом — реестр
  `OBYEKT_INDEKS` выдаёт отображаемое имя, короткое имя и регион;
- целостность связей проверяется функцией `moslikTekshiruvi()`, которая
  становится клиентской половиной серверных инвариантов раздела 6.

Замена состоит в том, что `MKB_DATA` начинает наполняться ответами API
вместо литералов. Сигнатуры полей сохраняются.

## 2. Общие соглашения

| Параметр | Значение |
|---|---|
| Базовый путь | `/api/v1` |
| Формат | `application/json; charset=utf-8` |
| Кодировка идентификаторов | строка, формат `GR-YYYY/NNNN`, `UI-YYYY/NNNN`, `IV-YYYY/NNNN`; в сегменте URL «/» кодируется как `%2F` либо используется дефисная форма `UI-YYYY-NNNN` |
| Даты | ISO 8601, `YYYY-MM-DD`; отметки времени — с часовым поясом `Asia/Tashkent` |
| Денежные суммы | целое число сумов, без разделителей; форматирование — на клиенте |
| Версионирование | путь (`/v1`); несовместимые изменения — только новый путь |

### 2.1 Пагинация и выборка

Списочные методы принимают `?limit` (по умолчанию 50, максимум 200),
`?cursor`, `?sort`. Ответ:

```json
{
  "data": [ ... ],
  "meta": { "jami": 1248, "cursor": "eyJpZCI6..." }
}
```

Курсорная пагинация выбрана вместо смещения: реестр меняется во время
просмотра, и `offset` даёт пропуски и повторы.

### 2.2 Ошибки

Единая оболочка, без исключений:

```json
{
  "xato": {
    "kod": "RUXSAT_YOQ",
    "xabar": "Bo'limga kirish huquqi yo'q",
    "tafsilot": { "bolim": "yuridik", "rol": "kredit" }
  }
}
```

| HTTP | `kod` | Когда |
|---|---|---|
| 400 | `NOTOGRI_SOROV` | не прошла валидация тела или параметров |
| 401 | `AUTENTIFIKATSIYA_YOQ` | нет сессии или истекла |
| 403 | `RUXSAT_YOQ` | роль не покрывает раздел или страницу |
| 404 | `TOPILMADI` | объект не существует либо скрыт правами |
| 409 | `HOLAT_MOS_EMAS` | переход этапа нарушает порядок раздела 4.5 ТЗ |
| 422 | `MOSLIK_BUZILDI` | нарушен инвариант раздела 6 |
| 429 | `JUDA_KOP_SOROV` | превышен лимит частоты |
| 500 | `ICHKI_XATO` | необработанный сбой; тело без деталей |

`404` вместо `403` для записей, скрытых правами: иначе перебор идентификаторов
раскрывает состав портфеля.

## 3. Аутентификация и сессии

```
POST /api/v1/kirish          { login, parol, ikkinchiOmil? }  -> сессия
POST /api/v1/chiqish                                          -> 204
GET  /api/v1/men                                              -> профиль + права
POST /api/v1/sessiya/yangilash                                -> продление
```

Требования:

- **А-1.** Сессия — в `HttpOnly`, `Secure`, `SameSite=Strict` cookie. Токен в
  `localStorage` не допускается: интерфейс полон пользовательского контента,
  и XSS не должен давать угон сессии.
- **А-2.** Срок жизни — 30 минут бездействия, максимум 12 часов.
- **А-3.** Второй фактор обязателен для ролей `admin` и `filial`.
- **А-4.** Пять неудачных попыток — блокировка учётной записи на 15 минут,
  событие в журнал аудита.
- **А-5.** `GET /men` возвращает роль и **вычисленный сервером** список
  разрешённых разделов. Клиент строит по нему меню, но не является источником
  истины.

```json
{
  "id": "USR-0041", "ism": "Ismoilov Otabek",
  "rol": "admin", "bolim": "Axborot texnologiyalari departamenti",
  "ruxsat": ["panel","portfel","aktivlar","yuridik",
             "realizatsiya","zaxira","hisobotlar","sozlamalar"],
  "korishRejimi": null
}
```

`korishRejimi` — роль, от имени которой администратор просматривает интерфейс
(Р-5 ТЗ). Подлинная роль остаётся в `rol` и именно она пишется в аудит.

## 4. Разграничение доступа

Клиентская матрица `ROL_RUXSAT` (`mkb.js`) — это **представление**. Сервер
обязан хранить собственную копию и проверять её на каждом запросе (Р-6 ТЗ).

| Роль | Разделы |
|---|---|
| `admin` | все |
| `filial` | panel, portfel, ta'minot, yuridik, realizatsiya, hisobotlar, sozlamalar |
| `kredit` | panel, portfel, ta'minot, hisobotlar, sozlamalar |
| `ta'minot` | panel, portfel, ta'minot, realizatsiya, hisobotlar, sozlamalar |
| `yurist` | panel, portfel, yuridik, realizatsiya, hisobotlar, sozlamalar |
| `tavakkal` | panel, portfel, zaxira, hisobotlar, sozlamalar |

- **Р-7.** Проверка выполняется до чтения из хранилища, а не при сериализации
  ответа.
- **Р-8.** Право на раздел не даёт права на запись. Модифицирующие методы
  перечисляют допустимые роли отдельно (колонка «Роли» в разделе 5).
- **Р-9.** Просмотр под чужой ролью (`korishRejimi`) сужает права до
  пересечения подлинной и выбранной роли и **никогда** не расширяет их.

## 5. Эндпоинты

### 5.1 Объекты залога и дела

| Метод | Путь | Роли | Назначение |
|---|---|---|---|
| GET | `/obyektlar` | все | реестр; фильтры `hudud`, `filial`, `bosqich`, `tur` |
| GET | `/obyektlar/{id}` | все | карточка объекта |
| GET | `/obyektlar/{id}/tarix` | все | история изменений |
| PATCH | `/obyektlar/{id}` | admin, ta'minot | правка атрибутов залога |
| GET | `/ishlar` | admin, filial, kredit, yurist, ta'minot | дела о взыскании |
| POST | `/ishlar/{id}/bosqich` | admin, yurist | перевод на следующий этап |

Переход этапа — отдельный метод, а не `PATCH` поля: он несёт побочные
эффекты (запись в историю, уведомления, проверка инвариантов) и должен быть
идемпотентным по заголовку `Idempotency-Key`.

```
POST /api/v1/ishlar/UI-2026-0412/bosqich
{ "bosqich": "musodara", "asos": "IH-2026/4471", "izoh": "..." }
```

Порядок этапов задан жёстко (раздел 5 ТЗ). Попытка перескочить — `409`.

### 5.2 Контроль залога

| Метод | Путь | Роли |
|---|---|---|
| GET | `/koriklar` · `/koriklar/{id}` | admin, ta'minot, filial, kredit |
| POST | `/koriklar` | admin, ta'minot |
| POST | `/koriklar/{id}/natija` | admin, ta'minot |
| GET | `/sugurtalar` | admin, ta'minot, filial, kredit |
| POST | `/sugurtalar/{id}/uzaytirish-talabi` | admin, ta'minot, kredit |
| GET | `/baholashlar` | admin, ta'minot, filial, tavakkal |
| POST | `/baholashlar/buyurtma` | admin, ta'minot (утверждение — filial) |
| GET/POST | `/hodisalar` | admin, ta'minot, yurist, filial |
| POST | `/hodisalar/{kod}/hal` | admin, ta'minot, yurist |

`POST /koriklar/{id}/natija` принимает акт осмотра: пункты проверки, балл
состояния, фотографии (через предподписанные URL), координаты и отметку времени
съёмки. Расхождение координат с адресом объекта более 500 м помечается в записи.

Закрытие события двухшаговое: `hal` (решено — доступно ta'minot/yurist, требует
непустых `xulosa` и `asos`) и финальное `yopish` (закрыто — только администратор).
`POST /hodisalar/{kod}/hal` требует непустых `xulosa` и `asos` — заключения и
основания закрытия; это уже реализовано в интерфейсе и дублируется сервером.

### 5.2а Классификация и резерв

| Метод | Путь | Роли |
|---|---|---|
| GET | `/tasnif` | admin, tavakkal, filial |
| GET | `/tasnif/normativlar` | admin, tavakkal |
| PATCH | `/tasnif/normativlar` | admin (журналируется с прежними значениями) |

Категория и резерв **вычисляются сервером** из дней просрочки и таблицы
нормативов; клиент их не присылает. Изменение нормативов — версионируемое:
прежние значения сохраняются с датой действия, пересчёт по портфелю выполняется
фоновым заданием с итоговым отчётом.

### 5.3 Маршруты инспекторов

| Метод | Путь | Роли |
|---|---|---|
| GET | `/marshrutlar/bugungi` | admin, ta'minot |
| POST | `/marshrutlar` | admin, ta'minot |

Формирование дневного маршрута инспектора из назначенных осмотров; мобильное
рабочее место (раздел 10) читает тот же ресурс.

### 5.4 Реализация и архив

| Метод | Путь | Роли |
|---|---|---|
| GET | `/auksion/lotlar` | admin, ta'minot, yurist, filial |
| POST | `/auksion/lotlar/{id}/bosqich` | admin, ta'minot |
| GET | `/arxiv` | admin, ta'minot, yurist, filial |

Записи архива доступны только на чтение — см. раздел 7.

### 5.5 Документы

| Метод | Путь | Роли |
|---|---|---|
| GET | `/hujjatlar` | по разделу объекта |
| POST | `/hujjatlar` | admin, yurist, ta'minot |
| GET | `/hujjatlar/{id}/yuklab` | по разделу объекта |

Загрузка: `POST` возвращает предподписанный URL объектного хранилища; файл
идёт мимо прикладного сервера. Ограничения — 25 МБ, типы `pdf, jpg, png,
docx, xlsx`, обязательная антивирусная проверка до перевода в статус
«доступен».

### 5.6 Служебные

| Метод | Путь | Роли |
|---|---|---|
| GET | `/portfel` | все | агрегаты и KPI |
| GET | `/hududlar` | все | разрез по регионам |
| GET | `/xarita/nuqtalar` | все | точки карты |
| GET | `/bildirishnomalar` | все | уведомления пользователя |
| GET | `/audit` | admin | журнал аудита |
| GET/POST/PATCH | `/foydalanuvchilar` | admin | учётные записи |

**Агрегаты считает сервер.** `/portfel` не отдаёт сырой список для суммирования
на клиенте — иначе разрез по 1248 объектам поедет с ростом портфеля, а
требование Д-7 («числа выводятся из массива») перестанет соблюдаться.

## 6. Инварианты, проверяемые сервером

Функция `moslikTekshiruvi()` в `malumot.js` — исполняемая спецификация. Каждая
её проверка обязана иметь серверный аналог, срабатывающий **до** записи:

1. `qarz.jami = qarz.asosiy + qarz.foiz` (Д-1);
2. состояние объекта выводится из этапа дела, а не хранится отдельно (Д-2);
3. этап `auksion` невозможен без даты приёма на баланс;
4. этапы `musodara` и `auksion` невозможны без исполнительного листа;
5. `ta'minot.baho > 0`, `qarz.kunlar > 0`;
6. сумма по разрезу состояний равна `portfel.jami`;
7. сумма по разрезу регионов равна `portfel.jami`;
8. разрезы контроля (осмотры, страховка, оценка) в сумме дают `portfel.jami`;
9. каждая ссылка `obyektId` разрешается в существующий объект;
10. статус земельного участка совпадает с этапом связанного дела;
11. категория качества соответствует дням просрочки, резерв — ставке категории;
12. страховое покрытие действующих полисов не ниже оценочной стоимости для
    страхуемых типов (земля не страхуется);
13. оценочная стоимость в карточке синхронна актуальной записи реестра оценок
    (на клиенте — производная, на сервере — проверка);
14. срезы договоров и должников внутренне сходятся; должников не больше,
    чем договоров.

Нарушение — `422 MOSLIK_BUZILDI` с перечнем несоблюдённых пунктов. Частичная
запись не допускается: транзакция откатывается целиком.

## 7. История изменений и неизменяемый архив

- **Х-1.** Каждое изменение объекта и дела порождает запись истории:
  кто, когда, какое поле, прежнее и новое значение, основание.
- **Х-2.** История доступна только на чтение; метода удаления нет.
- **Х-3.** Записи архива (`/arxiv`) неизменяемы. Исправление оформляется
  новой корректирующей записью со ссылкой на исходную.
- **Х-4.** Журнал аудита пишется в отдельное хранилище с правом только на
  добавление. Прикладная учётная запись СУБД не имеет `UPDATE`/`DELETE` на
  этой таблице.
- **Х-5.** Срок хранения истории и аудита — 7 лет, требует подтверждения
  службой комплаенса банка.

Текстовые формулировки в журнале аудита **не пересчитываются** при изменении
имени объекта: запись фиксирует состояние на момент действия. Это сознательное
исключение из правила Д-1, и оно отмечено в коде.

## 8. Интеграции

| Система | Направление | Содержание | Режим |
|---|---|---|---|
| АБС | входящее | договоры, остатки, просрочка, реквизиты должника | инкремент каждые 15 мин + полная сверка ночью |
| Кадастр | входящее | сведения по земельным участкам и недвижимости | по запросу, кеш 24 ч |
| МИБ | двустороннее | исполнительные производства, статусы | опрос 1 ч; приём вебхуков при их наличии |
| Страховые компании | двустороннее | статусы полисов, уведомления о продлении | по запросу + вебхуки при наличии |
| Оценочные организации | двустороннее | заказы оценки, готовые отчёты | по запросу, файлы через хранилище |

Требования:

- **И-1.** АБС — источник истины по договору и задолженности. Система не
  редактирует эти поля, а только отображает; попытка `PATCH` — `409`.
- **И-2.** Недоступность внешней системы не блокирует интерфейс. Показываются
  последние известные данные с явной отметкой времени получения.
- **И-3.** Каждый обмен фиксируется в аудите: направление, объём, результат.
- **И-4.** Расхождение с АБС по сумме задолженности порождает происшествие
  категории «сверка», а не тихую перезапись.

## 9. Уведомления

Каналы: внутренние сообщения, почта, СМС.

| Событие | Канал | Получатель |
|---|---|---|
| Событие по залогу высокой критичности | внутр. + СМС | залоговая служба, руководитель филиала |
| Истекает срок исполнительного листа (за 5 дней) | внутр. + почта | ответственный по делу |
| Объект переведён на новый этап | внутр. | ответственный, руководство |
| Страховка истекает (за 30 дней) | внутр. + почта | залоговая служба, кредитный менеджер |
| Оценка устаревает (за 90 дней) | внутр. | залоговая служба |

- **У-1.** Доставка — не более одного повторения в час по одному поводу.
- **У-2.** Отправка СМС протоколируется без текста сообщения.
- **У-3.** Пользователь управляет каналами, кроме событий высокой критичности —
  их отключение недоступно.

## 10. Мобильное рабочее место инспектора

Отдельное приложение поверх того же API, ограниченный набор методов:

```
GET  /mobil/vazifalar            назначенные выезды
GET  /mobil/obyektlar/{id}       карточка в сокращённом виде
POST /mobil/korik                результат осмотра: фото, координаты, отметки
POST /mobil/korik/{id}/imzo      подпись ответственного
```

- **М-1.** Работа офлайн: задания и карточки кешируются, результаты осмотра
  ставятся в очередь и отправляются при появлении связи.
- **М-2.** Фотография принимается только с координатами и отметкой времени
  устройства; расхождение с адресом объекта более 500 м помечается в записи,
  но не блокирует приём — связь и GPS в поле ненадёжны.
- **М-3.** Очередь переживает перезапуск приложения.

## 11. Нефункциональные требования

| Показатель | Значение |
|---|---|
| Время ответа списочных методов | 95-й процентиль ≤ 400 мс при 1248 объектах |
| Время ответа карточки | 95-й процентиль ≤ 250 мс |
| Одновременные пользователи | 150 |
| Доступность в рабочие часы | 99,5 % |
| Восстановление после сбоя | RPO 15 мин, RTO 2 ч |

Дополнительно:

- **Н-1.** Все запросы поверх TLS 1.2+; HTTP-порт только для редиректа.
- **Н-2.** Заголовки `Content-Security-Policy`, `X-Content-Type-Options`,
  `Referrer-Policy: same-origin`.
- **Н-3.** Ограничение частоты: 300 запросов в минуту на сессию,
  10 в минуту на методы аутентификации.
- **Н-4.** Персональные данные (ПИНФЛ, телефоны, адреса) не попадают в
  журналы приложения и в параметры URL.

## 12. Порядок перевода прототипа на API

| Шаг | Содержание | Признак завершения |
|---|---|---|
| 1 | Аутентификация и `/men`; меню строится по серверным правам | вход работает, разделы соответствуют роли |
| 2 | `/obyektlar`, `/obyektlar/{id}`, `/portfel` | реестр и панель на реальных данных |
| 3 | Остальные списки по разделу 5 | `malumot.js` не содержит литералов |
| 4 | Модифицирующие методы и переходы этапов | сценарии раздела 4.5 ТЗ проходят end-to-end |
| 5 | Интеграции по разделу 8 | ночная сверка с АБС расходится на 0 записей |
| 6 | Приёмочный прогон по разделу 7 ТЗ | протокол приёмки серверного этапа |

На шагах 1–3 `malumot.js` сохраняется как источник заглушек: модуль получает
переключатель `MKB_MANBA = "api" | "namuna"`. Это позволяет вести разработку
интерфейса и сервера параллельно и держать демонстрационный режим без
инфраструктуры.

## 13. Открытые вопросы к заказчику

Требуют решения до начала реализации:

1. Способ аутентификации: собственные учётные записи, доменные (LDAP/AD)
   или единый вход банка.
2. Наличие у АБС пригодного интерфейса выгрузки; при его отсутствии —
   согласование обмена файлами и его периодичности.
3. Модель интеграции с МИБ: опрос или вебхуки, состав передаваемых полей.
4. Видеоплатформа: производитель и протокол (RTSP, HLS, проприетарный SDK).
5. Требования службы информационной безопасности банка к хранению
   персональных данных и срокам ретенции.
6. Контур размещения: внутренний, облачный или смешанный.

Пункты 1, 2 и 6 блокирующие: без них нельзя зафиксировать ни схему
развёртывания, ни модель доступа.
