# Техническое задание
## Система цифрового контроля залоговых активов «Микрокредитбанк»

Версия 1.1 · Редакция от 24.08.2026

---

## 1. Назначение и границы

### 1.1 Что автоматизирует система

Жизненный цикл имущества, принятого банком в обеспечение по кредитным и лизинговым
договорам, с момента возникновения просрочки до реализации и передачи в архив:

```
Залог → Просрочка → Претензия → Иск → Решение суда → Исполнение МИБ →
Приём на баланс → Постановка под охрану → Мониторинг → Оценка → Аукцион → Архив
```

### 1.2 Что система НЕ делает

Не ведёт кредитный конвейер, не считает проценты, не формирует проводки, не заменяет
АБС. Она принимает данные о договоре и должнике из АБС и отвечает за физическую
сохранность обеспечения и его реализацию.

### 1.3 Границы текущей поставки

Поставляется интерактивный прототип интерфейса: полная навигация, все экраны,
работающая логика ролей и сценариев на клиенте. Серверная часть, интеграции и
персистентность — вне текущей поставки, требования к ним зафиксированы в разделе 8
как основание для следующего этапа.

## 2. Роли и разграничение доступа

| Роль | Зона ответственности | Разделы | Запрещено |
|---|---|---|---|
| **Администратор** | Учётные записи, справочники, журнал аудита | все 8 | — |
| **Руководство банка** | Портфель, эффективность взыскания, отчётность | все 8 | управление пользователями |
| **Специалист по взысканию** | Должники, договоры, претензии, суд, МИБ, аукцион | 6 | блок охраны, происшествия |
| **Оператор безопасности** | Наблюдение, тревоги, доступ на объекты | 5 | финансы, юридический блок, реализация |
| **Технический специалист** | Устройства, каналы связи, сервис | 4 | финансы, юридический блок, реализация, происшествия |

**Требования к разграничению:**

- Р-1. Пункт меню, недоступный роли, не отображается — не блокируется визуально, а отсутствует.
- Р-2. Прямой переход по URL в закрытый раздел возвращает состояние 403 с объяснением и путём выхода.
- Р-3. Ограничение действует на двух уровнях: раздел и отдельная страница (`data-ruxsat`).
- Р-4. Некорректная или отсутствующая роль трактуется как отсутствие доступа: переход на вход. Резервная роль — с наименьшими правами.
- Р-5. Администратор может просматривать интерфейс от имени другой роли; подлинная роль при этом сохраняется отдельно и не подменяется.
- Р-6. Клиентское разграничение — только представление. На следующем этапе дублируется серверной проверкой на каждом запросе.

## 3. Модель данных — единый источник

Ключевое требование, определяющее достоверность системы.

### 3.1 Принцип

Все страницы читают данные из **одного модуля** (`malumot.js`). Дублирование
массивов внутри страниц запрещено. Одна сущность — одна запись — одно значение
во всех разделах.

### 3.2 Сущности и связи

```
Mijoz (клиент) ──1:N── Shartnoma (договор) ──1:1── Garov (объект залога)
                              │                          │
                              └──1:1── Undiruv ishi      ├──1:N── Qurilma (устройство)
                                       (дело)            ├──1:N── Hodisa (происшествие)
                                       │                 └──1:N── Hujjat (документ)
                                       └──1:1── Auksion lot ──1:1── Arxiv yozuvi
```

### 3.3 Обязательные поля

**Mijoz:** идентификатор, тип (физ/юр), ФИО или наименование, ПИНФЛ/ИНН, филиал, контакты.

**Shartnoma:** номер, вид кредита, дата выдачи, сумма выдачи, остаток основного долга,
проценты и пеня, дней просрочки, ответственный специалист, клиент.

**Garov:** код, тип, наименование, адрес, площадь, оценочная стоимость, дата оценки,
статус жизненного цикла, дата приёма на баланс, страховка, договор.

**Undiruv ishi:** номер, этап, суд, номер решения, исполнительный лист, ближайший срок,
юрист, договор, история переходов между этапами.

**Auksion lot:** номер, начальная цена, дата торгов, участники, итоговая цена, покупатель.

### 3.4 Правила согласованности (проверяются автоматически)

- Д-1. Остаток долга в карточке объекта, в договоре и в деле совпадает до цифры.
- Д-2. Статус объекта соответствует этапу дела: этап «Исполнение МИБ» → статус «В процессе конфискации»; «Конфисковано» → «Под контролем банка».
- Д-3. Сумма по статусам в круговой диаграмме равна общему числу объектов; проценты в сумме дают 100.
- Д-4. Начальная цена лота равна оценочной стоимости объекта на дату оценки.
- Д-5. Даты монотонны: выдача < просрочка < претензия < иск < решение < исполнение < приём < аукцион.
- Д-6. Каждый объект в архиве имеет запись о деле и покупателе.
- Д-7. Числа в плитках показателей — результат подсчёта по массиву, а не записанная строка.
- Д-8. Вторичные списки (устройства, происшествия, документы, камеры, помещения, задачи)
  ссылаются на объект **идентификатором**, а не текстом. Отображаемое имя, короткое имя
  и регион выдаёт реестр объектов; хранить имя объекта во второй раз запрещено.

### 3.5 Реестр объектов

Правило Д-8 обеспечивается реестром `OBYEKT_INDEKS` в `malumot.js`. Он собирается
из трёх источников — активные записи, лоты реализации, архив — и выдаёт по коду
объекта его полное имя, короткое имя, тип, регион и изображение.

```
obyekt(id)             -> запись реестра или null
obyektNomi(id, qisqa?) -> отображаемое имя
obyektHududi(id, ...)  -> регион
joyNomi(id, внутри, разделитель?) -> «Navruz Plaza, 1-qavat»
```

Списки выбора объектов, регионов и филиалов на страницах не перечисляются вручную:
элемент помечается атрибутом `data-royxat="obyekt|obyekt-hammasi|hudud|filial"`,
и `mkb.js` наполняет его из реестра до навешивания обработчиков.

Исключение из Д-1 — журнал аудита: его формулировки фиксируют состояние на момент
действия и намеренно не пересчитываются при переименовании объекта.

## 4. Разделы и функциональные требования

### 4.1 Панель управления
Четыре рабочих места по ролям. Показатели считаются из данных. Карта с реальными
координатами объектов. Никаких сведений вне прав роли.

### 4.2 Залоговые объекты
Реестр с поиском, фильтрами по региону, типу и статусу; карточка объекта с вкладками
(общее, взыскание, документы, устройства, история); карта; помещения и этажи;
земельные участки. Переход из строки реестра в карточку сохраняет контекст фильтра.

### 4.3 Контроль безопасности
Пост наблюдения: видеостена 4/9 экранов, очередь тревог с нормативом реакции и
персональным закреплением, состояние каналов и резервного питания. Контроль доступа,
устройства, дистанционный осмотр, сервисные задания.

**Норматив:** приём тревоги — 3 минуты; превышение помечается и попадает в отчёт.

### 4.4 Происшествия
Регистрация, классификация по критичности, назначение ответственного, срок устранения,
связь с объектом и устройством, закрытие с заключением.

### 4.5 Взыскание
Цепочка из шести этапов со счётчиками и суммами. Дела, должники, договоры. Перевод
дела на следующий этап только по порядку, с записью в историю и уведомлением юриста.

### 4.6 Реализация
Приём конфиската мастером из четырёх шагов с обязательными документами; аукцион с
лотами, участниками и оформлением результата; постоянный архив только для чтения.

### 4.7 Отчёты
Финансовые показатели взыскания, центр отчётности с выгрузкой, документы, задачи
и согласования.

### 4.8 Настройки
Параметры, интеграции, журнал аудита, пользователи и роли (только администратор).

## 5. Требования к интерфейсу

### 5.1 Фирменный стиль
Цвета выведены из логотипа банка: основной `#0F5392`, дополнительный `#3AAA3E`.
Шрифт с поддержкой кириллицы и латиницы. Тёмная навигационная панель, светлая
рабочая область, тёмный фон для операционного поста наблюдения.

### 5.2 Обязательные нормы

- И-1. Контраст основного текста не ниже 4.5:1, крупного — 3:1 (WCAG AA).
- И-2. Минимальная область нажатия — 32×32 px, для основных действий — 40 px и выше.
- И-3. Горизонтальная прокрутка страницы недопустима на ширинах 1280–1920 px; широкие таблицы прокручиваются внутри своего контейнера.
- И-4. Цвет не может быть единственным носителем смысла: статус дублируется подписью.
- И-5. Видимый фокус на всех интерактивных элементах.
- И-6. Каждый интерактивный элемент даёт отклик: переход, изменение состояния или уведомление. Элементов без реакции нет.
- И-7. Вложенные интерактивные элементы одного типа запрещены (кнопка внутри кнопки разрывает разметку).
- И-8. Треки сетки, содержащие таблицы, объявляются как `minmax(0, …)`.

### 5.3 Двуязычность
Узбекский — исходный язык, русский — через словарь. Переключение без перезагрузки,
выбор сохраняется. Имена собственные, адреса, номера документов не переводятся.
Новый текст интерфейса добавляется в словарь одновременно с версткой.

### 5.4 Визуальный уровень
Объём вместо плоскости: градиентные плитки показателей, многослойные тени, объёмные
маркеры карты, диаграммы с градиентной заливкой и бликом. Единая пластика на всех
страницах — разнобой зрелости недопустим.

## 6. Требования к содержанию

- С-1. Данные правдоподобны для узбекского банка: реальные районы, типовая адресация, суммы в сумах в реалистичных диапазонах.
- С-2. Терминология соответствует практике: МИБ, исполнительный лист, претензия, ипотека, оборотные средства.
- С-3. В интерфейсе отсутствуют слова «демо», «пример», «образец», «тест», «прототип», заполнительный текст.
- С-4. Не используются эмодзи, дефолтные палитры фреймворков, служебные пути и имена инструментов разработки — ни в коде, ни в документации.
- С-5. Изображения-заглушки не повторяются: каждая камера, объект и превью — отдельный файл.

## 7. Критерии приёмки

| № | Проверка | Норма |
|---|---|---|
| П-1 | Все страницы отвечают, каркас на месте | 100% |
| П-2 | Ошибки в консоли | 0 |
| П-3 | Битые внутренние ссылки и изображения | 0 |
| П-4 | Неопределённые токены оформления | 0 |
| П-5 | Горизонтальная прокрутка на 1280/1440/1600/1920 | 0 страниц |
| П-6 | Интерактивные элементы без реакции | 0 |
| П-7 | Элементы меньше 32 px | 0 |
| П-8 | Закрытые для роли маршруты, отдавшие содержимое | 0 |
| П-9 | Расхождения по правилам согласованности данных (Д-1…Д-7) | 0 |
| П-10 | Маркеры происхождения (раздел С-4) | 0 |
| П-11 | Непереведённый текст интерфейса в русском режиме | 0 |
| П-12 | Контраст ниже AA | 0 |

Проверка П-6 выполняется реальным нажатием и фиксацией отклика, а не наличием
атрибута. Проверка П-9 — автоматическим сверением значений между разделами.

## 8. Следующий этап (вне текущей поставки)

- Серверная часть: авторизация, проверка прав на каждом запросе, журнал аудита.
- Интеграции: АБС (договоры и остатки), кадастр, МИБ, видеоплатформа, СКУД.
- Хранение: история изменений по каждому объекту и делу, неизменяемый архив.
- Уведомления: почта, СМС, внутренние сообщения по срокам и тревогам.
- Мобильное рабочее место инспектора для выездных осмотров.

## 9. План доведения текущего прототипа

| Этап | Содержание | Результат |
|---|---|---|
| 1 | Единый модуль данных, перевод всех страниц на него | Выполнение Д-1…Д-7 |
| 2 | Выравнивание пластики на 18 страницах прежней вёрстки | Единый визуальный уровень |
| 3 | Сплошная проверка нажатием, устранение элементов без отклика | П-6 = 0 |
| 4 | Пополнение словаря до полного покрытия | П-11 = 0 |
| 5 | Приёмочный прогон по таблице раздела 7 | Протокол приёмки |
| 6 | Реестр объектов, перевод вторичных списков на идентификаторы | Выполнение Д-8 |
| 7 | Оптимизация статических ресурсов | Вес каталога `assets` снижен с 39 до 2,9 МБ |
| 8 | Контракт серверного API | `docs/API.md` как основание этапа раздела 8 |

Этап 1 требует подтверждения заказчиком фактических значений: наименования этапов,
распределение типов обеспечения, диапазоны сумм, состав ответственных подразделений.
Без этого данные останутся правдоподобными, но вымышленными.
